# Requirements Document

## Introduction

Phase 5 of the DocOps platform adds a conversational memory/chat system that allows users to interact with their processed documents through a natural language chat interface. Users can create chat sessions scoped to a workspace, ask questions about extracted document data (trace fields), and maintain multi-turn conversations with context continuity. Session memory is persisted in DynamoDB, and responses are generated by Amazon Bedrock LLM with relevant trace data fed as grounding context.

## Glossary

- **Chat_Service**: The set of API handlers in the TypeScript API layer that manage chat session lifecycle and message exchange.
- **Session_Record**: A DynamoDB item in the `docops-sessions` table representing a chat session, keyed by `session_id`.
- **Memory_Entry**: An object containing `role` (`user` or `assistant`), `content` (message text), and `timestamp`, stored in the session's `memory` array.
- **Context_Retriever**: The component that fetches relevant extracted fields from workspace traces to provide grounding context for LLM responses.
- **Chat_Handler**: The component that orchestrates loading session memory, retrieving trace context, invoking Bedrock LLM, and storing the exchange.
- **Bedrock_Client**: The AWS Bedrock runtime client used to invoke the foundation model for generating conversational responses.
- **Workspace**: A tenant-scoped configuration unit that owns traces and sessions.
- **Trace_Record**: A DynamoDB item in the `docops-traces` table containing extracted document fields.
- **Token_Budget**: The maximum number of tokens allocated for the combined prompt (system prompt + context + memory + user message) sent to the LLM.

## Requirements

### Requirement 1: Create Chat Session

**User Story:** As a user, I want to create a new chat session for a workspace, so that I can start asking questions about my processed documents.

#### Acceptance Criteria

1. WHEN a POST request is made to `/v1/workspaces/:id/sessions` with an optional `title` field in the body, THE Chat_Service SHALL create a new Session_Record with a generated `session_id`, the workspace's `workspace_id`, an empty `memory` array, the provided title (or a default title), and a `created_at` timestamp.
2. THE Chat_Service SHALL return the created Session_Record with a 201 status code.
3. THE Chat_Service SHALL verify that the workspace exists and belongs to the requesting tenant before creating the session.
4. IF the workspace does not exist or belongs to a different tenant, THEN THE Chat_Service SHALL return a 403 Forbidden response.
5. THE Chat_Service SHALL store the `tenant_id` on the Session_Record to enable ownership verification on subsequent requests.

### Requirement 2: List Chat Sessions

**User Story:** As a user, I want to see all chat sessions for a workspace, so that I can resume a previous conversation.

#### Acceptance Criteria

1. WHEN a GET request is made to `/v1/workspaces/:id/sessions`, THE Chat_Service SHALL return all Session_Records matching the workspace_id, sorted by `created_at` descending (newest first).
2. THE Chat_Service SHALL include the total count of sessions in the response body.
3. THE Chat_Service SHALL verify that the workspace exists and belongs to the requesting tenant before returning results.
4. IF the workspace does not exist or belongs to a different tenant, THEN THE Chat_Service SHALL return a 403 Forbidden response.
5. THE Chat_Service SHALL return each session's `session_id`, `workspace_id`, `title`, `created_at`, and the count of Memory_Entry items in the memory array, without returning the full memory contents.

### Requirement 3: Get Session Details

**User Story:** As a user, I want to view a session's full message history, so that I can review past exchanges before continuing the conversation.

#### Acceptance Criteria

1. WHEN a GET request is made to `/v1/sessions/:id`, THE Chat_Service SHALL return the full Session_Record including the complete `memory` array.
2. IF the Session_Record does not exist for the given `session_id`, THEN THE Chat_Service SHALL return a 404 Not Found response.
3. THE Chat_Service SHALL verify tenant ownership by checking that the session's workspace belongs to the requesting tenant.
4. IF the session belongs to a different tenant, THEN THE Chat_Service SHALL return a 403 Forbidden response.

### Requirement 4: Send Chat Message

**User Story:** As a user, I want to send a message and receive an AI-generated response grounded in my document data, so that I can query my processed documents conversationally.

#### Acceptance Criteria

1. WHEN a POST request is made to `/v1/sessions/:id/chat` with a `message` field in the body, THE Chat_Handler SHALL load the Session_Record's existing memory array.
2. THE Context_Retriever SHALL fetch extracted fields from completed Trace_Records in the session's workspace to provide grounding context for the LLM.
3. THE Chat_Handler SHALL construct a prompt containing: a system instruction, the retrieved trace context, the session memory (previous messages), and the user's new message.
4. THE Bedrock_Client SHALL send the constructed prompt to the configured foundation model and return the generated response text.
5. THE Chat_Handler SHALL append two Memory_Entry items to the Session_Record's memory array: one with role `user` containing the sent message, and one with role `assistant` containing the generated response, each with a `timestamp`.
6. THE Chat_Service SHALL return the assistant's response text, the updated message count, and token usage metadata in the response body.
7. IF the `message` field is empty or missing, THEN THE Chat_Service SHALL return a 400 Bad Request response.
8. IF the Session_Record does not exist, THEN THE Chat_Service SHALL return a 404 Not Found response.
9. THE Chat_Service SHALL verify tenant ownership before processing the message.
10. IF the Bedrock_Client invocation fails, THEN THE Chat_Service SHALL return a 502 Bad Gateway response with an error message and SHALL NOT append any Memory_Entry items to the session.

### Requirement 5: Context Retrieval from Traces

**User Story:** As a user, I want the chat responses to be grounded in my actual document data, so that answers are accurate and relevant.

#### Acceptance Criteria

1. THE Context_Retriever SHALL query all Trace_Records with status `completed` in the session's workspace using the `workspace-index` GSI.
2. THE Context_Retriever SHALL extract the `fields` array from each completed Trace_Record and format the field names and values as structured text for the LLM context.
3. THE Context_Retriever SHALL include the `filename` and `trace_id` from each Trace_Record alongside its fields, so the LLM can reference specific documents.
4. IF no completed traces exist in the workspace, THEN THE Context_Retriever SHALL provide an empty context and THE Chat_Handler SHALL instruct the LLM to inform the user that no processed documents are available.
5. WHILE the total token count of the formatted context exceeds the context portion of the Token_Budget, THE Context_Retriever SHALL truncate by removing the oldest traces first until the context fits within budget.

### Requirement 6: Memory Management

**User Story:** As a user, I want long conversations to remain functional without degrading response quality, so that I can have extended multi-turn dialogues.

#### Acceptance Criteria

1. WHILE the total token count of the session memory exceeds the memory portion of the Token_Budget, THE Chat_Handler SHALL truncate the oldest Memory_Entry items from the beginning of the memory array, preserving the most recent exchanges.
2. THE Chat_Handler SHALL retain a minimum of the two most recent exchanges (four Memory_Entry items: two user, two assistant) regardless of token budget constraints.
3. THE Chat_Handler SHALL send only the truncated memory window to the LLM, while the full memory remains stored in the Session_Record for history retrieval.
4. THE Chat_Handler SHALL use a configurable token estimation method to approximate token counts for memory and context sizing.

### Requirement 7: Delete Chat Session

**User Story:** As a user, I want to delete a chat session I no longer need, so that my session list stays organized.

#### Acceptance Criteria

1. WHEN a DELETE request is made to `/v1/sessions/:id`, THE Chat_Service SHALL remove the Session_Record from the `docops-sessions` table.
2. THE Chat_Service SHALL return a 200 status code with a confirmation message on successful deletion.
3. IF the Session_Record does not exist, THEN THE Chat_Service SHALL return a 404 Not Found response.
4. THE Chat_Service SHALL verify tenant ownership before allowing deletion.
5. IF the session belongs to a different tenant, THEN THE Chat_Service SHALL return a 403 Forbidden response.

### Requirement 8: Workspace-Scoped Access Control

**User Story:** As a tenant, I want chat sessions to be scoped to my workspaces, so that I cannot access sessions or document data belonging to other tenants.

#### Acceptance Criteria

1. THE Chat_Service SHALL verify tenant ownership on every chat endpoint by checking that the session's workspace belongs to the requesting tenant.
2. IF a request targets a Session_Record whose workspace belongs to a different tenant, THEN THE Chat_Service SHALL return a 403 Forbidden response.
3. THE Chat_Service SHALL use the existing tenant resolution middleware to identify the requesting tenant from the JWT token.
4. THE Context_Retriever SHALL only retrieve Trace_Records from the workspace associated with the session, preventing cross-workspace data leakage.

### Requirement 9: Bedrock LLM Integration

**User Story:** As a platform operator, I want chat responses generated by a managed LLM service, so that the system provides high-quality conversational answers without self-hosted model infrastructure.

#### Acceptance Criteria

1. THE Bedrock_Client SHALL invoke the Amazon Bedrock `InvokeModel` API using the model ID configured in the `BEDROCK_MODEL_ID` environment variable.
2. THE Bedrock_Client SHALL send the prompt using the Anthropic Claude Messages API format with `role` and `content` fields.
3. THE Bedrock_Client SHALL set a maximum output token limit of 1024 tokens per response.
4. THE Bedrock_Client SHALL include a system prompt instructing the model to answer questions based on the provided document context and to state when information is not available in the context.
5. IF the Bedrock API returns a throttling error, THEN THE Bedrock_Client SHALL retry the request once after a 1-second delay before returning an error.
